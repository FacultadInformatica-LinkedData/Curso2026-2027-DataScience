1.4 Observations on data quality

  • PLANTA, ESCALERAS and FAX are empty in every row, so we leave them out of the ontology. LOCALIDAD and PROVINCIA are always "MADRID".
  • We read the CSV using Windows-1252 encoding. Empty cells are counted after trimming whitespace. District names equal to "DISTRITO" are treated as unknown. Neighbourhood names are converted to uppercase for counting, so "Buenavista" and "BUENAVISTA" are counted together.
  • The dataset is updated daily, so the generated RDF may become outdated.
  • PK is the unique identifier of each row, so we use it to build the URIs. Every row is one park or garden.
  • LATITUD and LONGITUD are floats.
  • ACCESIBILIDAD contains the codes 0, 1 and 2. We keep the source codes as strings rather than converting them to a boolean.
  • COD-BARRIO, COD-DISTRITO and CODIGO-POSTAL are stored as strings to preserve leading zeros.

3. Resource naming strategy

  • Domain: http://parquesmadrid.example.org. This is an example domain for the assignment; no service has been deployed.
  • URI form: ontology terms use hash URIs (/ontology/parques#ParqueJardin); data uses slash URIs (/resource/...).
  • Patterns:
    • Park: /resource/parque/{PK}, e.g. /resource/parque/5986859
    • District: /resource/distrito/{COD-DISTRITO}, e.g. /resource/distrito/21
    • Neighbourhood: /resource/barrio/{COD-DISTRITO}-{COD-BARRIO}, e.g. /resource/barrio/21-1
  • Why these choices: we use the ids from the dataset instead of names, because names have spaces, accents and may change, and we can use their codes consistently. A neighbourhood code is only unique within its district, so we combine both codes. Resource paths are lowercase and have no file extension. Ontology terms keep their declared spelling, such as ParqueJardin.

If a district or neighbourhood code is missing, we omit that link until the code can be checked. We do not create URIs from empty values or guess codes from names.

Content negotiation: if the data were published, the server would use the HTTP Accept header to offer HTML (text/html) or Turtle (text/turtle). Resource URIs would return a 303 See Other redirect to the selected description. Requests to the ontology document would return its HTML or Turtle representation; the fragment identifies the individual term. This is the proposed publication strategy, not an implemented server.

4. Ontology summary

  • Classes: ParqueJardin, Distrito, Barrio.
  • Object properties: enDistrito, enBarrio, barrioDeDistrito.
  • Datatype properties: nombre, descripcion, horario, equipamiento, transporte, accesibilidad, urlContenido, nombreVia, claseVial, numero, codigoPostal, latitud, longitud, coordenadaX, coordenadaY, telefono, email; codigoDistrito, nombreDistrito; codigoBarrio, nombreBarrio.
  • PK is used in park URIs. We leave out the empty fields PLANTA, ESCALERAS and FAX, and the constant fields LOCALIDAD and PROVINCIA. For this lightweight model we also leave out PUERTA, ORIENTACION, TIPO-NUM and TIPO. We use DESCRIPCION for the description and do not model DESCRIPCION-ENTIDAD separately.
