Group03 – Analysis of the data sources, licensing and resource naming strategy (Hands-on Assignment 2)

This document contains the analysis of the two datasets selected in Hands-on 1 (see requirements/datasetRequirements.html), the analysis of their licensing, and the resource naming strategy for the ontology and the data that we will generate. The ontology is in ontology/airquality.ttl and a sample instantiation in ontology/airquality-example.ttl.

The figures in section 1 were computed by us over the files that are in the csv/ directory. When something could not be confirmed with the data or with the documentation of the portal, we say so.

From this comparison, the codes 6 (CO) and 14 (O3) are confirmed by the data, and codes 1, 9, 10 and the group 20/30/35 are consistent with SO2, PM2.5, PM10 and BTX. The meaning of 7, 8 and 12 (NO, NO2 and NOx according to the usual coding of the Madrid network) comes from our general knowledge and is not confirmed by the files. For this reason the sample instantiation only uses magnitude 6. The differences between the files (PM in stations 4, 54 and 60, SO2 in station 4) may be due to the files being updated on different dates.

1.4 Quality issues found

  • Three formats of coordinates in dataset A (degrees-minutes-seconds with two quoting styles, projected with decimal comma, decimal degrees). We use the decimal degrees.
  • Dataset A: the station Juan Carlos I has no street class, particle or name (and its street code is 1111); Plaza Elíptica has no street particle.
  • Dataset B is in wide format: it must be reshaped to one observation per hour.
  • Flag M appears 3 times and its meaning is not documented in the files. The meaning of V and N is also not documented in the files (V is by far the most frequent). We keep the flag as it is, without interpreting it.
  • The value 0 appears in every magnitude; we cannot tell from the data whether it is a measured zero or a missing value.

Potential licence for the generated dataset

We propose to publish the generated dataset under CC BY 4.0. Reasons: (1) both sources use CC BY 4.0, which allows us to adapt the data (transform it to RDF and link it) and to publish the result; (2) the only condition of the sources is attribution, so a licence with the same condition is enough and a more restrictive one (for example share-alike) is not needed; (3) it keeps the generated dataset easy to reuse. The attribution will say that the data come from the Ayuntamiento de Madrid (datos.madrid.es) and were transformed to RDF by Group03.

3. Resource naming strategy

3.1 Decisions

  • Domain: http://airquality.group03.example.org/. It is not the default domain of Protégé. It uses the reserved name example.org because the group does not own a domain, so these URIs are not dereferenceable.
  • Different paths: ontology resources (classes and properties) use the path ontology/; individuals use the path resource/.
  • Hash URIs for ontology terms (ontology/airquality#Station) and slash URIs for individuals (resource/Station/28079004), following the guidelines of the course. The ontology is small and is always read as a whole, so hash URIs are suitable. Individuals, in particular the hourly measurements, are numerous and each one must have its own URI, so slash URIs are used.
  • One path per class of individuals: Station/, StationType/, Pollutant/, Municipality/ and Measurement/, so that two individuals of different classes can never have the same URI.
  • Property URIs independent of class URIs: properties are defined directly in the ontology namespace (aq:hasAltitude), not inside the URI of a class.
  • Identifiers: taken from the data when the data have a stable one, so that anyone can build the URI from the source file.
  • Naming conventions: classes start with a capital letter and properties with a lower-case letter, both in camel case (Station, hasStationCode). All labels of the ontology are in English.

Note on pollutant identifiers. Dataset A names the pollutants (NO2, SO2, CO, PM10, PM2.5, O3, BTX) and dataset B identifies them only by magnitude code. For a code, the pollutant individual is the one whose name corresponds to that code (see section 1.3); for example code 6 corresponds to Pollutant/CO. Codes 7, 8 and 12 will get their individuals when their meaning is confirmed. Codes 20, 30 and 35 appear in the same stations as BTX, which in dataset A is a single group, so each of these codes will need its own individual once its meaning is confirmed; Pollutant/BTX is only used for the column of dataset A.

3.3 Content negotiation

The design for publication (a later assignment) is that the URI of an individual identifies the real-world thing and answers with a redirection to a representation chosen from the Accept header: HTML for people (text/html) and RDF in Turtle (text/turtle) for applications. The ontology URI would answer in the same way. This is a design decision; it is not implemented yet.

4. Ontology and linking

The ontology has 5 classes (Station, StationType, Pollutant, Municipality, Measurement), 5 object properties and 13 datatype properties; every property has one domain and one range. It does not mix languages in its labels.

Following the feedback of Hands-on 1, the linking will be done between entities, not between values such as coordinates. The classes prepared for linking are:

  • aq:Municipality: the individual for Madrid can be linked to the Wikidata item for Madrid (wd:Q2807 in the course slides), and to DBpedia and GeoNames.
  • aq:Pollutant: the pollutants can be linked to the Wikidata items of each chemical compound or particle type.
  • aq:Station: stations located in a named place (for example Parque del Retiro or Casa de Campo) can be linked to the entity of that place.
